# 04 剧情

> 叙事自增长层：`nrt-narrative-grower` 分析叙事图缺口 → 生成创意草案 → 审批 → apply 写回叙事基础层。
> 草案以 **Markdown 文件**形式存于 `02_剧情数据/`，**不写入图数据库**。与 [叙事基础.md](叙事基础.md)（事实层）、[角色美术.md](角色美术.md) 互补。

---

## 概述

剧情层定义两类产物：

- **选择分叉图节点（Choice）**：剧情层首个图节点，把 galgame「玩家选择分叉」一等公民化（定义见下文「选择分叉图节点」）。
- **叙事草案（Narrative Draft，Markdown 文件）**：承载 `nrt-narrative-grower` 的 analyze→generate→apply 闭环，**不作为图节点存在**——流程状态（status / applied_at 等）存在 MD 文件的 YAML frontmatter，创意正文与分析存在 Markdown 正文。

**status 语义（草案 frontmatter）**：`10` 待审 / `11` 批准 / `0` 驳回 / `-1` 作废。

> **applied 用独立字段，不占 status 值**：apply 成功后写 frontmatter `applied_at`（非空 = 已应用），保持 status 取值集合稳定。

生命周期：`generate`（skill 侧，写 `02_剧情数据/<日期_概述>.md`，frontmatter `status=10`）→ **人工审批**（手动把 frontmatter `status` 由 `10` 改 `11` / 驳回改 `0`）→ `apply`（skill 侧，`status=11` 后从 MD 正文提取基础节点写回叙事基础层 + 回写 frontmatter `applied_at`）。

---

## 产物：叙事草案（`02_剧情数据/<日期_概述>.md`）

每次 analyze→generate 产出一个 `.md` 文件，**文件名 = `YYYY-MM-DD_<概述>.md`**（日期取自 `created_at`，概述取自标题核心主题，清洗 Windows 非法字符）。frontmatter 的 snowflake `id` 仅作稳定唯一锚点，不参与文件名。apply 后从正文提取为基础节点写回。

### 文件结构

YAML frontmatter（流程状态）+ Markdown 正文（创意草案 + 分析）：

```markdown
---
id: <draft_id>
title: '<标题>'
status: 10              # 10 待审 / 11 批准 / 0 驳回 / -1 作废
created_at: '<ISO 时间戳>'
applied_at: null        # null=未应用；apply 成功后写 ISO 时间（应用标记）
applied_node_ids: ''    # apply 写入的基础节点 id，分号分隔
---

# <标题>

<创意草案正文：拟增角色/事件/地点/信息及关系，apply 据此提取>

## 分析依据（analyze）

<人类可读摘要；growth_opportunities 的 summary/suggestions/details 可作参考置于正文>
```

### frontmatter 字段

| 字段 | 中文 | 类型 | 必填 | 说明 |
|------|------|------|------|------|
| id | 编号 | string | 否 | snowflake Base62，稳定唯一锚点（**非文件名**；文件名=日期+概述） |
| title | 标题 | string | 是 | 草案标题 |
| status | 流程状态 | int | 否 | `10` 待审 / `11` 批准 / `0` 驳回 / `-1` 作废 |
| created_at | 创建时间 | string | 否 | ISO 时间（generate 写入） |
| applied_at | 应用时间 | string | 否 | null=未应用；apply 成功后写 ISO 时间（**应用标记**） |
| applied_node_ids | 应用节点 | string | 否 | apply 写入的基础节点 id，分号分隔 |

### 正文语义

| 正文 | 中文 | 说明 |
|------|------|------|
| 草案正文 | 创意内容 | 自然语言，含拟增角色/事件/地点/信息及关系；apply 据此提取 |
| 分析依据 | analyze 摘要 | growth_opportunities 的人类可读摘要（可选附 JSON） |

**status 枚举**：`10` 待审 → `11` 批准 →（apply 回写 `applied_at`）；`10` → `0` 驳回。

## 边

剧情层的图边来自 **Choice 选择点**（`presents` / `option`，见下「选择分叉图节点」）。**叙事草案不建任何图边**：

- 草案本身不是图节点，与既有实体之间没有边（无 `proposed_for`）。
- apply 后产生的基础节点之间，用叙事基础层的边（relation / involved / occurred_at / at / link / evt_relation）自连，保持基础层纯净。
- 溯源用 frontmatter 的 `applied_node_ids` 字段（apply 写入的节点 id 列表）。

---

## 文件名与 ID

- **文件名**：`YYYY-MM-DD_<概述>.md`（日期取自 `created_at`，概述取自标题核心主题，清洗 Windows 非法字符）——草案的用户面标识，apply 据此 Glob 定位文件。
- **frontmatter `id`**：snowflake Base62，全局唯一无前缀（同叙事基础层），仅作稳定唯一锚点（文件改名/复制后仍可追溯），**不参与文件名**：

```bash
python "${CLAUDE_SKILL_DIR}/../../scripts/snowflake_base62.py" -n 1 -q
```

## 选择分叉（Choice）图节点

> galgame「选择点」一等公民化。大纲设定：灵魂穿越者只能在关键选择节点干预，而关键选择节点 = 玩家的选择项。Choice 把「玩家在此选择、不同选项导向不同后续」显式建模。

### 节点：Choice（选择点）

最小粒度：一个玩家选择分叉点。

| 字段 | 中文 | 类型 | 必填 | 示例 |
|------|------|------|------|------|
| id | 编号 | string | 是 | snowflake Base62 |
| name | 名称 | string | 是 | `跳江选择` / `三选一` |
| description | 情境 | string | 否 | 选择发生的情境描述 |
| time | 时间 | string | 否 | `Day 0 深夜` / `Day 22` |

### 边

#### presents — 事件触发选择 `N:N`

- **方向**：`Event → Choice`

| 属性 | 中文 | 类型 | 必填 | 说明 |
|------|------|------|------|------|
| sync | 同步 | boolean | 否 | 默认 `false` |

> 某事件播放到此呈现选择。事件是源头（上游），选择由事件触发（下游），符合全局上游→下游。

#### option — 选项导向后续 `N:N`

- **方向**：`Choice → Event`

| 属性 | 中文 | 类型 | 必填 | 说明 |
|------|------|------|------|------|
| label | 选项文本 | string | 是 | 玩家看到的选项：`再想想` / `跳江` / `选苏晓禾` |
| leads_to_ending | 导向结局 | boolean | 否 | 默认 `false`；`true` 表示该选项进入结局 |
| detail | 详情 | string | 否 | |
| sync | 同步 | boolean | 否 | 默认 `false` |

> 选择是因（上游），选完进入的事件是果（下游）。事件流嵌入：`Event -presents-> Choice -option-> Event`，Choice 作为分叉点嵌在事件链中间。

### 与 evt_relation 的分工

- `evt_relation`（Event→Event，叙事基础层）：事件链内部的因果 / 先后 / 时序串联。
- `Choice + presents + option`（剧情层）：管「在哪选择、选项导向哪条分支」，是分叉发源点。
- 分支点原先靠 `evt_relation{type:包含}` + title 文案后缀（「（分支A）」「BE」）hack，现由 `option` 边承载分支语义；主线 `先后 / 因果` 不受影响。

### 结局

结局不单独建节点，仍用叙事基础层的 `Event` 表达，加可选属性 `ending_kind`（`BE`/`TE`/`HE`/`NE`，见 [叙事基础.md](叙事基础.md)）。`option{leads_to_ending:true}` 指向的 Event 即结局事件。

## 章节编排（Chapter）图节点

> galgame 运行时剧本的**编排设计层锚点**。Chapter 在图中只存编排信息（标题/序号/场景顺序/分支骨架摘要），对话内容不入图——完整逐句对话存于剧本 JSON（见 [剧本.md](../剧本.md)）。运行时只读 JSON，图作设计/编排/依赖追踪层。

### 章节（Chapter）

最小粒度：一个剧本章节文件对应的编排单元。

| 字段 | 中文 | 类型 | 必填 | 示例 |
|------|------|------|------|------|
| id | 编号 | string | 是 | snowflake Base62 |
| title | 标题 | string | 是 | `新皮肤·Day0` |
| chapter_no | 章节序号 | int | 是 | `1` |
| script_path | 剧本路径 | string | 否 | `99_game/data/chapters/chapter01_新皮肤.json` |
| summary | 概要 | string | 否 | 本章叙事范围一句话（时间/地点/核心事件），编剧的创作纲要 |
| branch_summary | 分支骨架 | string | 否 | 主线/分支/结局简述（如「主线跳江未遂→BE跳下/TE生还」） |
| status | 流程状态 | int | 否 | `0` |

**status 枚举**：`0` 待编排 → `1` 剧本草稿已生成 → `2` 已通过 validate 校验 → `10` 待审 → `11` 批准。驳回归 `0`，作废 `-1`。

> Chapter 是**生产节点**（产出 JSON 交付物，需审批），与 DesignSheet/IllusDesign 同级，由 `screenwriter` skill 推进。`target_status=2`（默认）时 screenwriter 写草稿 + 跑 `validate_chapter.py`，通过则写 `10`（待审）；`target_status=1` 时仅写草稿 `1`。`2` 为可选中间态（已校验未提交），由 dashboard 手动 submit 路径使用。

### 边

#### contains — 章节包含场景 `N:M`

- **方向**：`Chapter → Scene`

| 属性 | 中文 | 类型 | 必填 | 说明 |
|------|------|------|------|------|
| order | 序号 | int | 否 | 该场景在章节 scene-block 序列中的首次出现位置（JSON 的完整序列为运行时权威） |
| sync | 同步 | boolean | 否 | 默认 `false`（编排引用，不级联） |

> 章节编排引用其用到的 Scene（Scene 已由 `Location -[has_scene]-> Scene` 存在）。一个 Scene 可被多个 Chapter 引用。同一 Scene 在一章内重复出现时，MERGE 合为一条边，完整序列以剧本 JSON 为权威。

#### depicts — 场景引用立绘 `N:N`

- **方向**：`Scene → StandingIllustration`

| 属性 | 中文 | 类型 | 必填 | 说明 |
|------|------|------|------|------|
| sync | 同步 | boolean | 否 | 默认 `false`（引用边，不级联） |

> 表示「该场景的剧本需要此立绘变体可用」。编剧（`screenwriter`）据剧本 `say` 指令的 `<who>.<portrait>` 创建此边；若目标 StandingIllustration 不存在，screenwriter 兜底建节点（`status=0`）+ `expands_to`/`ref_style` 边，交由 `char-stand-designer` 推进出图。这是立绘按需生成的入度依据（原 TODO 的落地）。
